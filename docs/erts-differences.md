# ERTS Differences

PBeam follows the ERTS implementation model and observable behavior. This file lists each intentional difference from ERTS and OTP. Add a row in the same PR that adds a difference. Remove the row in the same PR that removes the difference.

| Area | PBeam behavior | ERTS behavior | Reason |
| --- | --- | --- | --- |
| Scheduling | One scheduler thread. A process runs until it waits or exits. There are no reductions and no preemption. | Many scheduler threads. Each process gets a reduction budget and yields when the budget is used. | The process runtime (#49) needs only cooperative processes for OTP IO. |
| Exit signals | An abnormal exit that reaches a linked process without `trap_exit` returns a runtime error. | The exit signal kills the linked process, and the signal propagates to its links. | Exit signal propagation is not necessary for the current fixtures. |
| Signal queue | A process has no signal queue. Links, unlinks, exits, monitors, demonitors, and group-leader changes take effect at once, and `EXIT` and `DOWN` go straight into the mailbox as messages. `erts_internal:group_leader/2` never returns `false`, so the `erts_internal:group_leader/3` reply path does not run. `erlang:process_info/2` reads another process at once. | Every message and control signal reaches a process through one incoming signal queue (`erl_proc_sig_queue.c`), ordered for each sender and receiver pair. The receiver handles control signals before message matching; they never enter the mailbox. A control reply comes back as a message with a fresh reference and is received selectively. `process_info/2` sends a process-info signal and waits for the reply when the other process is busy or exiting (`erl_bif_info.c:1387-1397`). | One scheduler thread cannot show the difference. #10 adds the signal queue, because two scheduler threads make signal order and handling time observable. |
| Receive timeout | A `wait_timeout` instruction with the timeout `infinity` waits as `wait` does. A `wait_timeout` with the timeout `0` or another value returns the runtime error `unsupported receive timeout`. A `receive ... after 0` with a literal `0` compiles to `timeout` without `wait_timeout`, and it runs. | With `0`, `wait_timeout` continues at once at the next instruction, `timeout`. With a finite timeout, it starts a timer, and the process continues at the next instruction when the timer expires. With `infinity`, it waits for a message without a timer. A value that is not a valid timeout raises `timeout_value` (`msg_instrs.tab`). | PBeam has no timers. `gen_statem:loop/3` waits with the `hibernate_after` option, which is `infinity` by default. (#76) |
| Heap limit | There is no `max_heap_size` process flag and no heap accounting. | `max_heap_size` can stop a process when its heap gets too large. Messages count toward the heap only when `message_queue_data` is `on_heap`. | PBeam uses Rust memory management, not a per-process heap. |
| Process and reference counters | Process identifiers and references come from `u64` counters. Counter overflow returns a runtime error. | The number of live processes is limited by `+P` (default 1048576). Process table slots are used again. | A `u64` counter does not overflow in practice. |
| Term order | The `is_lt` and `is_ge` instructions and the BIF `erlang:'>='/2` compare two terms in the ERTS term order, and `put_map_exact` sorts its keys in the ERTS flatmap key order. When the result depends on the order of two different references, `is_lt`, `is_ge`, `erlang:'>='/2`, and `put_map_exact` return the runtime error `unsupported term order of two references`. | ERTS orders two references by the reference counter of the scheduler thread that made each one, then by the thread number (`erts_set_ref_numbers` in `erl_bif_unique.h`, `ref_common` in `erts_cmp_compound` in `utils.c`). Thus a reference that a process on scheduler 1 makes later can be less than a reference that a process on scheduler 2 made earlier. | PBeam has one scheduler and one reference counter, so it cannot give the ERTS order of two references. No current fixture path compares two references. (#77, #110) |
| Integer range | PBeam stores an integer as a 64-bit signed value. `erlang:'+'/2` and `erlang:'-'/2` with a result outside -(2^63) to 2^63 - 1 return a runtime error. Integers from 2^59 to 2^63 - 1, and from -(2^63) to -(2^59) - 1, give the same results as in ERTS. An instruction operand outside the 64-bit range, such as `{integer,18446744073709551616}` in `gc_bif` or `is_lt`, loads. The instruction returns the runtime error `unsupported BEAM integer operand outside the 64-bit range: needs a bignum` when it reads the operand. | An integer outside the small-integer range -(2^59) to 2^59 - 1 is a bignum. `erlang:'+'/2` and `erlang:'-'/2` make a bignum when the result is not a small integer (`erl_arith.c:378-384`, `erl_arith.c:591-597`). The loader adds an integer operand outside this range to the literal area as a bignum (`marshal_integer` in `beam_file.c:2132-2214`). For example, `net:shortest_matching_prefix/3` has the operand 2^128 - 1 in `bsl` (`net.erl:865`). | PBeam has no bignum term yet. No integer on the measured start path of #79 leaves the 64-bit range. (#110) |
| Chardata conversion | `unicode:characters_to_binary/2` supports only the `unicode` and `utf8` encodings. It converts a binary or a proper list of integers, binaries, and nested lists. Any other encoding returns a runtime error. A code point that is not a Unicode scalar value, a run of adjacent binaries that is not valid UTF-8, and a term that is not chardata each return a runtime error. A valid binary gives an equal copy of the binary. | The BIF converts `latin1`, `unicode`, and `utf8` in C, and `unicode:characters_to_binary_int/2` converts the other encodings. Invalid input gives `{error, Converted, Rest}`, an incomplete UTF-8 sequence at the end gives `{incomplete, Converted, Rest}`, and a term that is not chardata raises `badarg`. A valid binary, or a list with only one valid binary, gives the same binary. A list can have a binary as its tail. | On the current fixture paths, `io:io_request/2` calls the BIF with `unicode`, and `group:putc_request/3` calls it with `utf8`, each with valid chardata. PBeam has no improper lists yet. (#74, #77) |
| Local call to a BIF stub | A local call from a module to its own function whose export is a BIF runs the BEAM body of that function. For example, a local call from `erts_internal:term_to_string/1` to `term_to_string/2` runs the stub body. Only `call_ext`, `apply`, `apply_last`, the `bif` instructions, a `call_fun` or `call_fun2` of an external fun, and the calls of `erlang:apply/2` and `erlang:apply/3` go to the BIF. | The loader replaces the body of each function whose export is a BIF (`ops.tab`, `emu_load.c`). A local call also runs the BIF: `erts_internal:term_to_string/1` returns `"{a,1}"` for `{a,1}`. | No function on the current fixture paths makes a local call to a BIF stub. (#74, #76) |
| Spawn of a BIF | A process that `spawn/3`, `spawn_link/3`, or `spawn_opt/4` starts with a BIF as its MFA runs the BEAM stub body of that function when its module is loaded. When the module is not loaded, the spawn returns the runtime error `unresolved external MFA`. For example, `spawn_monitor(maps, keys, [not_a_map])`, which calls `spawn_opt/4` in `erlang.beam`, runs the `maps` stub, or fails when `maps` is not loaded. A process that starts at `erlang:apply/2` or `erlang:apply/3`, as `erlang:spawn/1` makes, runs its body in `erlang.beam`, which runs the `i_apply_fun` or `i_apply` instruction, as in ERTS. | The new process calls the export of the MFA, and the export of a BIF goes to the BIF (`emu_load.c`). `spawn_monitor(maps, keys, [not_a_map])` gives the `DOWN` reason `{{badmap, not_a_map}, [{maps, keys, [not_a_map], ...}]}`. | No process on the current fixture paths starts with a BIF as its MFA. (#74) |
| Node of a term | `erlang:node/1` accepts only a pid and returns `nonode@nohost`. Any other argument returns a runtime error. | `node/1` returns the node of a pid, a port, or a reference, and raises `badarg` for other terms. Without distribution the node is `nonode@nohost`. | Only `io:io_request/2` calls `node/1` on the current fixture paths, with a pid. (#74) |
| BIF arguments | `erlang:'++'/2` with a list that is not empty on the left and a term that is not a list on the right returns a runtime error. With a pid and a valid item, `erlang:process_info/2` returns `undefined` for a process that is not alive, the item `registered_name` of each live process, and the item `current_stacktrace` of the calling process. For a live process, a list of items, the item `{dictionary, Key}`, and each other item return a runtime error. | `[1] ++ x` returns the improper list `[1\|x]`. `lists:keyfind/3` also accepts an improper list: it returns a tuple that it finds before the improper tail, and it raises `badarg` when it finds no tuple. `lists:member/2` also accepts an improper list: it returns `true` when it finds the element before the improper tail, and it raises `badarg` when it does not find the element. `process_info/2` also returns the other items, accepts a list of items for a live process, and returns `current_stacktrace` of another process (`process_info_bif` in `erl_bif_info.c`). | PBeam has no improper lists yet. On the `gen_statem` enter-loop path, `process_info/2` gets `self()` and `current_stacktrace`. On the group path, `group:server_name/0` gets `self()` and `registered_name`. The `prim_tty` writer gets the pid of its parent and `registered_name` (`prim_tty.erl:569-571`). (#76, #77, #108) |
| Exception stack trace | PBeam gives each `error` exception the stack trace `[]`: in the uncaught exit reason `{Reason, []}` and in the catch value `{'EXIT', {Reason, []}}`. `erlang:process_info(self(), current_stacktrace)` returns `{current_stacktrace, []}`, and `current_stacktrace` of another live process returns a runtime error. Thus `gen_statem:terminate/7` gets the stack trace `[]` and stops the server with `erlang:Class(Reason)` through `apply_last`, not with `erlang:raise/3`. The exit reason is the same. | ERTS records the frames, the BIF arguments, and the `error_info` location. The stack trace of `erlang:nif_error/1` starts with the `erlang:nif_error/1` frame. `process_info(self(), current_stacktrace)` returns the frames of the caller, so `gen_statem:terminate/7` runs `erlang:raise(Class, Reason, Stacktrace)`. `current_stacktrace` of another process returns the frames of that process. | PBeam records no stack frames yet. `build_stacktrace` and `raise` are not implemented yet. No start-path code reads `current_stacktrace` of another process. (#73, #76, #108) |
| Exception raise sites | Only `erlang:nif_error/1`, `erlang:exit/1`, `erlang:error/3`, and the `badarg` exceptions of `erlang:'++'/2`, `lists:keyfind/3`, `erlang:element/2`, `erlang:tuple_size/1`, `erlang:register/2`, `erlang:whereis/1`, `lists:member/2`, `erlang:process_info/2`, `erlang:iolist_to_iovec/1`, `erlang:function_exported/3`, `erlang:tl/1`, `erlang:length/1`, `erlang:atom_to_list/1`, `erlang:list_to_atom/1`, and the `apply` and `apply_last` instructions, the `badarg` and `system_limit` exceptions of `erlang:apply/2` and `erlang:apply/3`, the `system_limit` exception of `erlang:list_to_atom/1`, the `badfun` and `badarity` exceptions of the `call_fun` and `call_fun2` instructions and of `erlang:apply/2`, the `badarg` exceptions of `erlang:is_function/2` and `erlang:make_fun/3`, the `badarith` exceptions of `erlang:'+'/2` and `erlang:'-'/2`, the `badmap` and `badkey` exceptions of `erlang:map_get/2` and the `put_map_exact` instruction, and the `badmap` exception of `maps:merge/2`, raise an exception that `try` and `catch` can catch. Each of these sites returns a runtime error instead: the `raise` instruction (a `try` that rethrows an exception of a class that no clause matches, and the cleanup of `try ... after`), `badmatch`, `case_end`, `try_case_end`, `if_end`, `badrecord`, `function_clause` (`func_info`), `undef` for an external function or an external fun whose function is not loaded, `badmap` in `put_map_assoc` and in `maps:keys/1`, and calls to `erlang:error/1,2` and `erlang:throw/1`. The `throw` class is not implemented. | Each site raises an exception in the calling process. `raise` raises the original class again, and the other sites raise class `error` with the reason `{badmatch, V}`, `{case_clause, V}`, `if_clause`, `{badrecord, V}`, `function_clause`, `undef`, `{badmap, M}`, `{badkey, K}`, `badarg`, or `{try_clause, V}`. `erlang:error/3` raises class `error` with its first argument as the reason. `erlang:throw/1` raises class `throw`. `try` and `catch` can catch each of them. | Task #73 adds the exception model and the raises of `erlang:nif_error/1` and `erlang:exit/1`. Task #76 adds the `badarg` raises of the BIFs and the `apply` instructions on the `gen_statem` enter-loop path. Task #77 adds the `badarg` raises of `erlang:tuple_size/1`, `erlang:register/2`, `lists:member/2`, and `erlang:process_info/2`. Task #78 adds the `badarg` raise of `erlang:iolist_to_iovec/1`. Task #63 adds the raise of `erlang:error/3`. Task #108 adds the `badarg` raise of `erlang:whereis/1`. Task #109 adds the `badarg` and `system_limit` raises of `erlang:apply/2` and `erlang:apply/3`, the `badfun` and `badarity` raises of `call_fun`, `call_fun2`, and `erlang:apply/2`, and the `badarg` raises of `erlang:is_function/2` and `erlang:make_fun/3`. Task #110 adds the `badarith` raises of `erlang:'+'/2` and `erlang:'-'/2`. Task #111 adds the `badarg` raises of `erlang:tl/1`, `erlang:length/1`, `erlang:atom_to_list/1`, and `erlang:list_to_atom/1`, the `system_limit` raise of `erlang:list_to_atom/1`, the `badmap` and `badkey` raises of `erlang:map_get/2` and `put_map_exact`, and the `badmap` raise of `maps:merge/2`. |
| Process names | `erlang:register/2` gives a name to a process, and an exit frees the name. `erlang:whereis/1` returns the pid of a name or `undefined`, and raises `badarg` for a term that is not an atom. PBeam has no ports, so a name never gives a port. `erlang:unregister/1` and `erlang:registered/0` return the runtime error `unresolved external MFA`. A `send` to an atom returns the runtime error `unsupported BEAM send target`. | `whereis/1` returns the pid or port of a name or `undefined`, `unregister/1` frees a name, and `registered/0` returns all names. A send to a registered name delivers the message, and a send to a name that is not registered raises `badarg`. | The current fixtures register names, look up names, read `registered_name`, and free a name with an exit only. No fixture path calls `unregister/1` or `registered/0`, or sends a message to a name. (#77, #108) |
| Spawn options | `erlang:spawn_opt/4` accepts only the options `link` and `monitor`. Any other option returns a runtime error. A spawn with the `monitor` option returns `{Pid, Reference}`. | `spawn_opt/4` also accepts `{monitor, Options}`, `priority`, `fullsweep_after`, `min_heap_size`, `min_bin_vheap_size`, `max_heap_size`, `message_queue_data`, and `async_dist`. An option that is not valid raises `badarg`. | Only `erlang:spawn_monitor/3` calls `spawn_opt/4` on the current fixture paths, with `[monitor]`. (#87) |
| Instruction calls | An external call to `erlang:apply/2` or `erlang:apply/3` runs as the ERTS `i_apply_fun` or `i_apply` instruction. An external call to `erlang:yield/0` or `erlang:hibernate/0` returns the runtime error `unsupported instruction call`. The `apply` and `apply_last` instructions call the function through the same path as `call_ext`, so an `apply` of `erlang:apply/2` or `erlang:apply/3` runs that apply, and an `apply` of `erlang:yield/0` or `erlang:hibernate/0` returns this error. | The loader turns these calls into the `i_apply_fun`, `i_apply`, `i_yield`, and `i_hibernate` instructions (`ops.tab`). They call the function, let other processes run, or hibernate the process. `apply` and `apply_last` with `erlang:apply/2` or `erlang:apply/3` run that apply (`fixed_apply` in `beam_common.c`). | No current fixture path calls `erlang:yield/0` or `erlang:hibernate/0`. Their bodies in `erlang.beam` call themselves, so PBeam must not run them as BEAM code. #109 adds `erlang:apply/2` and `erlang:apply/3`. (#87, #76, #109) |
| NIF stubs | PBeam loads no NIF library. It links `prim_tty:write_nif/2` as a native binding that is active when the module loads, and each entry to the function runs it in place of the BEAM stub. PBeam has no NIF resource term, so no term is a TTY resource, and the binding raises `error:badarg` and writes nothing. A call to each other function in `-nifs` runs its BEAM stub body. `erlang:load_nif/2` returns the runtime error `unresolved external MFA`. | `erlang:load_nif/2` loads the NIF library, and each NIF replaces the stub body of its function. During the OTP boot, `standard_error:server/0` (standard_error.erl:70) and `user_drv:init/1` (user_drv.erl:182) call `prim_tty:load/0` (prim_tty.erl:197-202). `prim_tty:tty_create/1` makes the TTY resource, and `write_nif/2` writes to it. | PBeam has no NIF loading and no NIF resources yet. `tty_create/1` is not exported, and only `prim_tty:init/1` calls it (prim_tty.erl:220), so a TTY resource and the host write become reachable only when the OTP IO servers start. Task #79 adds `tty_create/1`, the other start-path NIFs, and the host write. (#63, #50) |
| Error report | PBeam writes no report for an uncaught exception. | ERTS logs `Error in process <pid> with exit value: ...` for an uncaught `error` exception (and for an uncaught `throw` as `nocatch`), but not for class `exit`. Under `erl -noshell`, the report goes to stdout. | PBeam has no logger output path yet. (#73) |
| Initial group leader | The first process is its own group leader, as the ERTS `init` process is. No `user` process exists. | A process started by `erl -eval` has the registered `user` process as its group leader. | Starting the OTP standard IO servers is not implemented yet; task #79 owns it. (#72) |
| Map keys | A map key must be an integer or an atom. A hashmap (more than 32 keys) accepts atoms and integers in the ERTS small-integer range, -(2^59) to 2^59 - 1. A BEAM map literal loads an integer key only in 0..255 (`SMALL_INTEGER_EXT`). `INTEGER_EXT` and bignum literals are not supported yet. Each unsupported case returns a runtime error. | A map accepts any term as a key. A hashmap hashes a bignum or compound term with `make_internal_hash`. | PBeam has no ERTS hash for bignums or compound terms yet. The current fixtures use integer and atom keys only. (#75) |
| Atom table | The atom table starts with the 1150 static atoms, then holds the atoms of each module in load order. Each run of `BeamProgram::execute` starts with a copy of this table, and `erlang:list_to_atom/1` puts a new atom into the table of the run, so `BeamProgram::atom` does not find it. `erlang:system_info(os_type)` puts `unix` and the flavor atom into the table of the run at its first call. PBeam does not create the atoms of emulator start and OTP boot. `BeamProgram::load` loads all modules at the start, in the given order. A literal that PBeam cannot decode yet does not create its atoms after the unsupported part. Thus an atom that is not static can get a different index than on ERTS. This changes the hashmap order of non-static atom keys, and the flatmap order of two atom keys that ERTS creates in a different order. | At `-eval` time the table holds about 10966 atoms on macOS and 10342 on Linux. The atoms from index 1150 depend on the platform and the build. After about index 3740 their order changes from run to run. In interactive mode a module loads at its first call. ERTS makes `unix` and the flavor atom at emulator start (`os_info_init` in `erl_bif_info.c:6418-6440`). | PBeam does not run the emulator start or the OTP boot, and it has no code loading on demand. Even ERTS has no stable index for these atoms. (#84, #111) |
| System information | `erlang:system_info/1` supports only the item `os_type`. It returns `{unix, Flavor}`, where `Flavor` is the `uname` system name in lowercase, for example `{unix,darwin}` on macOS. Each other item returns the runtime error `unsupported erlang:system_info/1 argument ...`, also an item that ERTS rejects with `badarg`. PBeam reads the system name with the Unix `uname` call, so it supports only Unix hosts and always returns the family `unix`. | `system_info/1` returns many other items, for example the string `"29"` for `otp_release`, and raises `badarg` for an item that it does not know (`system_info_1` in `erl_bif_info.c`). On Windows, `os_type` is `{win32, nt}`. | Only `os:type/0` calls `system_info/1` on the measured start path of #79, from `prim_tty:init_term/1` (`prim_tty.erl:284`). (#111) |
