# ERTS Differences

PBeam follows the ERTS implementation model and observable behavior. This file lists each intentional difference from ERTS and OTP. Add a row in the same PR that adds a difference. Remove the row in the same PR that removes the difference.

| Area | PBeam behavior | ERTS behavior | Reason |
| --- | --- | --- | --- |
| Scheduling | One scheduler thread. A process runs until it waits, calls `erlang:hibernate/0`, or exits. There are no reductions and no preemption. | Many scheduler threads. Each process gets a reduction budget and yields when the budget is used. | The process runtime (#49) needs only cooperative processes for OTP IO. |
| Exit signals | `erlang:exit/2` sends an exit signal to a local pid as ERTS does. A reference that is an active alias sends the exit signal to the owner of the alias, and another reference gives `true` with no signal. An exit signal through an alias of the caller that ends the caller (`kill`, or a reason that is not `normal` without `trap_exit`) returns the runtime error `unsupported exit signal through an alias of the caller`. An abnormal exit that reaches a linked process without `trap_exit` returns a runtime error. | The exit signal kills the linked process, and the signal propagates to its links. A reference is never `exit2_suicide` (`bif.c:1750-1772`), so `erlang:exit/2` through an alias of the caller returns `true`, and the caller ends when it next handles signals (measured: the next `receive` ends the caller with `killed`). | Task #135 adds `erlang:exit/2`. Task #153 adds exit signals through an alias. Link exit propagation is not necessary for the current fixtures. The exit of the caller through its own alias needs the signal queue (#10). |
| Signal queue | A process has no signal queue. Links, unlinks, exits, monitors, demonitors, and group-leader changes take effect at once, and `EXIT` and `DOWN` go straight into the mailbox as messages. `erts_internal:group_leader/2` never returns `false`, so the `erts_internal:group_leader/3` reply path does not run. `erlang:process_info/2` reads another process at once. | Every message and control signal reaches a process through one incoming signal queue (`erl_proc_sig_queue.c`), ordered for each sender and receiver pair. The receiver handles control signals before message matching; they never enter the mailbox. A control reply comes back as a message with a fresh reference and is received selectively. `process_info/2` sends a process-info signal and waits for the reply when the other process is busy or exiting (`erl_bif_info.c:1387-1397`). The receiver checks a message to an alias when it handles the message signal, and drops it when the alias is not active then (`erl_proc_sig_queue.c:6026-6070`). | PBeam checks a message to an alias when it is sent, and a `DOWN` message ends a `demonitor` or `reply_demonitor` alias when it goes into the mailbox (#153). A send from another process gives the ERTS result, because the receiver handles its signals before it runs again (`erl_process.c:10321-10350`). A send to an alias of the sender does not. Measured on ERTS 29.1.1: `A = erlang:monitor(process, P, [{alias, demonitor}]), A ! m, erlang:demonitor(A, [flush])` drops `m`, but PBeam keeps it. After `A ! m1, A ! m2` with `reply_demonitor`, `erlang:demonitor(A, [info])` returns `true` and no message stays on ERTS; PBeam returns `false` and keeps `m1`. The `noproc` `DOWN` messages of the monitors of a process also arrive later and in another order on ERTS. After `R = erlang:monitor(process, Dead)`, also for a name that no process has and for a port name, `erlang:demonitor(R, [info])` returns `true` and no `DOWN` message stays on ERTS 29.1.1. PBeam puts the `noproc` `DOWN` message into the mailbox at once and keeps no monitor, so `erlang:demonitor(R, [info])` returns `false`, and `erlang:demonitor(R)` keeps the `DOWN` message. #10 adds the signal queue, which makes signal order and handling time the same as ERTS. |
| Timers | PBeam has one timer queue on the run clock. The run clock is the ERTS internal monotonic time: one second at the run start, in nanoseconds, from `std::time::Instant`. A receive timer of `wait_timeout` and a BIF timer of `erlang:start_timer/3` end at a clock tick of 1 ms, as in ERTS. Timers with the same end always expire in start order. PBeam reads the clock and expires each due timer before it takes the next process, so a timer never expires while a process runs. When no process can run, PBeam sleeps until the first timer end. The run ends when no process can run and no timer is active. Thus a process that starts a timer again at each expiry keeps the run alive. | Each scheduler has a timer wheel, and a timer with a time of `ERTS_TIMER_WHEEL_MSEC` or more is a high-level timer in a tree of the scheduler (`erl_time.h:156`, `erl_hl_timer.c:2617`, `2774`). A scheduler reads the clock and bumps its timers after `ERTS_CHECK_TIME_REDS` reductions and before it sleeps (`erl_process.c:9797-9810`, `3452-3620`). A timer that ends less than 2¹⁴ clock ticks (16384 ms) after the wheel position goes to the tail of its soon wheel slot (`time.c:647-668`, `1256-1300`), so these timers expire in start order. A timer with a later end starts in the later wheel. ERTS moves it to the tail of its soon wheel slot about 8 to 16 seconds before its end (`time.c:95-113`, `1030-1130`), so it can expire after a timer with the same end that started later (measured: a timer `a` of 20000 ms and, 3700 ms later, a timer `b` with the same end expire as `[b,a]`). A timer can expire while its receiver runs on another scheduler. ERTS corrects the Erlang monotonic time, and the node does not end when no process can run. | PBeam has one scheduler thread and no reductions (see "Scheduling"). No measured path observes the ERTS time correction. No measured path starts a timer of 16384 ms or more: the `supervisor` hibernate timer is 1000 ms, the `logger_olp` idle timeout is 100 ms, and the `logger_h_common` file sync timer is 5000 ms. (#150) |
| Clocks | `erlang:monotonic_time/1` reads the run clock of "Timers" and adds the ERTS offset, so the Erlang monotonic time at the run start is -576460752000000000 in `native`, as at the ERTS emulator start. The run clock starts at each `BeamProgram::execute`. PBeam has no time correction, so the Erlang monotonic time follows the host monotonic clock. `os:system_time/1` reads the host `CLOCK_REALTIME`, as ERTS does. `erts_internal:perf_counter_unit/0` always returns 1000000000. | The clock starts at the emulator start. The Erlang monotonic time at the start is `ERTS_MONOTONIC_TIME_START_EXTERNAL`, -576460752000000000 (`erl_time.h:318-321`, `331-340`; measured: `erlang:system_info(start_time)`). With time correction, the default, ERTS adjusts the Erlang monotonic time to the OS system time (`check_time_correction` in `erl_time_sup.c:450-777`). `erts_internal:perf_counter_unit/0` returns `ERTS_HRTIME_UNIT`, 1000000000, on a host without `rdtscp`, such as the pinned aarch64 host (measured), and the measured TSC frequency on a host with `rdtscp` (`sys_time.c:1032-1041`). | One `BeamProgram::execute` is one run, as one emulator is in ERTS. No measured path observes the time correction: `logger` reads the clocks only for timestamps (`logger.erl:728-729`, `logger_olp.hrl:75`, `logger_std_h.erl:850-851`). No measured path reads the `perf_counter` unit. (#154) |
| Heap limit | There is no `max_heap_size` process flag and no heap accounting. | `max_heap_size` can stop a process when its heap gets too large. Messages count toward the heap only when `message_queue_data` is `on_heap`. | PBeam uses Rust memory management, not a per-process heap. |
| Process and reference counters | Process identifiers and references come from `u64` counters. Counter overflow returns a runtime error. | The number of live processes is limited by `+P` (default 1048576). Process table slots are used again. | A `u64` counter does not overflow in practice. |
| Term order | The `is_lt` and `is_ge` instructions and the BIF `erlang:'>='/2` compare two terms in the ERTS term order, and `put_map_exact` sorts its keys in the ERTS flatmap key order. When the result depends on the order of two different references, `is_lt`, `is_ge`, `erlang:'>='/2`, and `put_map_exact` return the runtime error `unsupported term order of two references`. | ERTS orders two references by the reference counter of the scheduler thread that made each one, then by the thread number (`erts_set_ref_numbers` in `erl_bif_unique.h`, `ref_common` in `erts_cmp_compound` in `utils.c`). Thus a reference that a process on scheduler 1 makes later can be less than a reference that a process on scheduler 2 made earlier. | PBeam has one scheduler and one reference counter, so it cannot give the ERTS order of two references. No current fixture path compares two references. (#77, #110) |
| Integer range | PBeam stores an integer as a 64-bit signed value. `erlang:'+'/2`, `erlang:'-'/2`, `erlang:'*'/2`, and `erlang:'div'/2` with a result outside -(2^63) to 2^63 - 1 return a runtime error. Integers from 2^59 to 2^63 - 1, and from -(2^63) to -(2^59) - 1, give the same results as in ERTS. An instruction operand outside the 64-bit range, such as `{integer,18446744073709551616}` in `gc_bif` or `is_lt`, loads. The instruction returns the runtime error `unsupported BEAM integer operand outside the 64-bit range: needs a bignum` when it reads the operand. `erlang:monotonic_time/1` and `os:system_time/1` with `perf_counter`, or with a positive integer unit other than 1, 1000, 1000000, and 1000000000, trap to `erlang:convert_time_unit/3`, which multiplies the time by the unit before it divides. When the product is outside the 64-bit range, `erlang:'*'/2` returns the runtime error. With `perf_counter`, the product is always outside the range, so `erlang:monotonic_time(perf_counter)` and `os:system_time(perf_counter)` always return the runtime error. | An integer outside the small-integer range -(2^59) to 2^59 - 1 is a bignum. `erlang:'+'/2`, `erlang:'-'/2`, `erlang:'*'/2`, and `erlang:'div'/2` make a bignum when the result is not a small integer (`erl_arith.c:378-384`, `erl_arith.c:591-597`, `erl_arith.c:117-143`). The loader adds an integer operand outside this range to the literal area as a bignum (`marshal_integer` in `beam_file.c:2132-2214`). For example, `net:shortest_matching_prefix/3` has the operand 2^128 - 1 in `bsl` (`net.erl:865`). The `erlang:convert_time_unit/3` trap of `erlang:monotonic_time/1` and `os:system_time/1` (`erl_time_sup.c:2342-2348`) makes a bignum product (`erlang.erl:5333-5336`). | PBeam has no bignum term yet. No integer on the measured start path of #79 leaves the 64-bit range. (#110, #154) |
| Chardata conversion | `unicode:characters_to_binary/2` supports only the `unicode` and `utf8` encodings. It converts a binary or a list of integers, binaries, and nested lists, and a list can have a binary as its tail. Any other encoding returns a runtime error. A term that is not chardata raises `badarg`, as the `utf8_need` walk of ERTS decides. A code point that is not a Unicode scalar value and a run of adjacent binaries that is not valid UTF-8 each return a runtime error. A valid binary gives an equal copy of the binary. | The BIF converts `latin1`, `unicode`, and `utf8` in C, and `unicode:characters_to_binary_int/2` converts the other encodings. Invalid input gives `{error, Converted, Rest}`, an incomplete UTF-8 sequence at the end gives `{incomplete, Converted, Rest}`, and a term that is not chardata raises `badarg`. A valid binary, or a list with only one valid binary, gives the same binary. A list can have a binary as its tail. | On the current fixture paths, `io:io_request/2` calls the BIF with `unicode`, and `group:putc_request/3` calls it with `utf8`, each with valid chardata. The error tuples come with their first consumer. (#74, #77, #152) |
| Local call to a BIF stub | A local call from a module to its own function whose export is a BIF runs the BEAM body of that function. For example, a local call from `erts_internal:term_to_string/1` to `term_to_string/2` runs the stub body. Only `call_ext`, `apply`, `apply_last`, the `bif` instructions, a `call_fun` or `call_fun2` of an external fun, and the calls of `erlang:apply/2` and `erlang:apply/3` go to the BIF. | The loader replaces the body of each function whose export is a BIF (`ops.tab`, `emu_load.c`). A local call also runs the BIF: `erts_internal:term_to_string/1` returns `"{a,1}"` for `{a,1}`. | No function on the current fixture paths makes a local call to a BIF stub. (#74, #76) |
| Spawn of a BIF | A process that `spawn/3`, `spawn_link/3`, or `spawn_opt/4` starts with a BIF as its MFA runs the BEAM stub body of that function when its module is loaded. When the module is not loaded, the spawn returns the runtime error `unresolved external MFA`. For example, `spawn_monitor(maps, keys, [not_a_map])`, which calls `spawn_opt/4` in `erlang.beam`, runs the `maps` stub, or fails when `maps` is not loaded. A process that starts at `erlang:apply/2` or `erlang:apply/3`, as `erlang:spawn/1` makes, runs its body in `erlang.beam`, which runs the `i_apply_fun` or `i_apply` instruction, as in ERTS. | The new process calls the export of the MFA, and the export of a BIF goes to the BIF (`emu_load.c`). `spawn_monitor(maps, keys, [not_a_map])` gives the `DOWN` reason `{{badmap, not_a_map}, [{maps, keys, [not_a_map], ...}]}`. | No process on the current fixture paths starts with a BIF as its MFA. (#74) |
| Node of a term | `erlang:node/1` accepts only a pid and returns `nonode@nohost`. Any other argument returns a runtime error. | `node/1` returns the node of a pid, a port, or a reference, and raises `badarg` for other terms. Without distribution the node is `nonode@nohost`. | Only `io:io_request/2` calls `node/1` on the current fixture paths, with a pid. (#74) |
| BIF arguments | With a pid and a valid item, `erlang:process_info/2` returns `undefined` for a process that is not alive, the item `registered_name` of each live process, and the item `current_stacktrace` of the calling process. For a live process, a list of items, the item `{dictionary, Key}`, and each other item return a runtime error. | `process_info/2` also returns the other items, accepts a list of items for a live process, and returns `current_stacktrace` of another process (`process_info_bif` in `erl_bif_info.c`). | On the `gen_statem` enter-loop path, `process_info/2` gets `self()` and `current_stacktrace`. On the group path, `group:server_name/0` gets `self()` and `registered_name`. The `prim_tty` writer gets the pid of its parent and `registered_name` (`prim_tty.erl:569-571`). (#76, #77, #108) |
| Exception stack trace | PBeam gives each `error` exception the stack trace `[]`: in the uncaught exit reason `{Reason, []}` and in the catch value `{'EXIT', {Reason, []}}`. The exception is the `undef` of a function that a loaded module does not export: it gets the stack trace `[{Module, Function, Args, []}]`, with no caller frames after this frame (see "Undefined functions"). `build_stacktrace` gives the stack trace that PBeam keeps in `x2`, so `try ... catch Class:Reason:Stack` gets `[]` or this one frame. `erlang:process_info(self(), current_stacktrace)` returns `{current_stacktrace, []}`, and `current_stacktrace` of another live process returns a runtime error. `erlang:raise/3` checks its stack trace argument, and the exception gets the stack trace `[]`, also through `build_stacktrace`. Thus `gen_statem:terminate/7` gets the stack trace `[]` and stops the server with `erlang:Class(Reason)` through `apply_last`, not with `erlang:raise/3`. The exit reason is the same. | ERTS records the frames, the BIF arguments, and the `error_info` location. The stack trace of `erlang:nif_error/1` starts with the `erlang:nif_error/1` frame. `process_info(self(), current_stacktrace)` returns the frames of the caller, so `gen_statem:terminate/7` runs `erlang:raise(Class, Reason, Stacktrace)`. `current_stacktrace` of another process returns the frames of that process. `erlang:raise/3` gives the exception its stack trace argument, at most `backtrace_depth` frames, with each `{M, F, A}` and `{Fun, Args}` frame changed to have the location `[]`. | PBeam records no stack frames yet. The `raise` instruction is not implemented yet. No start-path code reads `current_stacktrace` of another process. #166 adds `build_stacktrace` and the `undef` frame. (#73, #76, #108, #166) |
