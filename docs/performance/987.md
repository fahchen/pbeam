# 2026-10-23 JST - Read the clock after `ERTS_CHECK_TIME_REDS` reductions, task [#987](https://github.com/fahchen/pbeam/issues/987), pull request [#1108](https://github.com/fahchen/pbeam/pull/1108)

Task #987 is an ERTS behavior change. Before it, the scheduler loop read the OS monotonic clock before each process that it took. Now the loop reads the clock only after its processes used 4000 actual reductions after the last read, as `erl_process.c:9803-9810` does. Each other read of the clock (a timer start, `erlang:monotonic_time/0,1`, the sleep of an idle scheduler) also sets the last time and sets the count to 0, as `erts_get_monotonic_time` does (`erl_time_sup.c:279-280`).

## Measurement

Release builds on one host, one scheduler. "before" is the branch with the two loop reads set back to `Timers::now`; the reduction count stays in it. Each round ran `pbeam pp_bench run -- pp_bench.beam erlang.beam` for each build in turn and measured the wall time of the command. Three sessions of 15 rounds each ran. The sessions did not record the host load.

The probe module is not a committed fixture. It sends 300000 messages between two processes in short turns, so the loop takes about 600000 processes:

```erlang
-module(pp_bench).
-export([run/0]).
run() -> S = self(), P = spawn(fun() -> peer(S) end), loop(P, 300000).
loop(_, 0) -> ok;
loop(P, N) -> P ! ping, receive pong -> loop(P, N - 1) end.
peer(S) -> receive ping -> S ! pong, peer(S) end.
```

| Session | before median | after median | before min | after min |
| --- | --- | --- | --- | --- |
| 1 | 567.7 ms | 486.2 ms | 299.8 ms | 270.5 ms |
| 2 | 283.6 ms | 261.0 ms | 278.7 ms | 255.7 ms |
| 3 | 280.2 ms | 259.2 ms | 273.8 ms | 255.3 ms |

These numbers are an observation only. The sessions do not obey the rules of `docs/performance-status.md`, so this record makes no speed claim.

## Decision

Land the change as a behavior change: ERTS has this rule. The decision does not depend on the timing.

## Known gaps

- The sessions kept no raw file and no host load.
- PBeam does not add the reductions of a signal handling at schedule in for a process that then does not run (`erl_process.c:10441-10444`).
