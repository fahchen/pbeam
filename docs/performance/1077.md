# 2026-10-24 JST - Keep `ordered_set` keys in a balanced tree, task [#1077](https://github.com/fahchen/pbeam/issues/1077)

Before this change, an `ordered_set` table kept its keys in a sorted `Vec<Term>` (PR #1074). An insert or a delete of a new key moved each key after it, so it cost O(n). Now the keys go in a std `BTreeSet`, so an insert, a delete, and a lookup cost O(log n), as the AVL tree of `erl_db_tree.c` does. A walk step (`ets:next/2`) costs O(log n), as `find_next` does (`erl_db_tree.c:3659-3762`).

## Measurement

Release builds on one host (Apple M1 Max, arm64, macOS), one scheduler. "before" is `cd8ca596` (main). "after" is `acd7231d`. Each round ran `pbeam os_bench run <N> -- os_bench.beam ets.beam erlang.beam` once for each key count and each build in turn, and measured the wall time of the command. One session of 5 rounds. The probe module is not a committed fixture. It inserts N keys from N down to 1 (each insert goes before each stored key), looks up each key, walks the table with `ets:first/1` and `ets:next/2`, and deletes each key:

```erlang
run(Arg) ->
    N = list_to_integer(atom_to_list(Arg)),
    T = ets:new(t, [ordered_set, public]),
    ins(T, N), look(T, N), walk(T, ets:first(T)), del(T, N),
    0 = ets:info(T, size), ok.
```

| Keys | before median | after median | before min | after min |
| --- | --- | --- | --- | --- |
| 10 | 13.1 ms | 12.8 ms | 12.2 ms | 12.0 ms |
| 10 000 | 50.7 ms | 39.3 ms | 49.1 ms | 38.4 ms |
| 100 000 | 1831.9 ms | 290.5 ms | 1756.4 ms | 287.9 ms |

The wall time includes the start of the runtime and the load of the modules, about 12 ms. With 10 keys the difference is in the noise. The cost of "before" grows by about 36 times from 10 000 to 100 000 keys, and the cost of "after" grows by about 7 times.

## Decision

Land the change. The observable results do not change: the key order, the walks, and the select continuations use the same ERTS term order, and the ets integration tests pass without a change.

## Known gaps

- One session only, with no raw file, no one-minute load value, and no statement that the host ran nothing else. The record does not meet the landing rule of `docs/performance-status.md`; the gain at 100 000 keys (about 6 times) is far beyond the spread of the rounds, and the change also lands as the O(log n) data structure that the task asks for.
- Each key holds an `Arc` of the atom table, 8 bytes more than a `Term` for each key. `ets:info(T, memory)` counts these bytes; it does not match the ERTS words (row "ETS tables" of `docs/erts-differences.md`).
- `ets:slot/2` still walks the keys from the first key, as before.
