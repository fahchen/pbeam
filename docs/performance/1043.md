# 2026-10-23 JST - Keep the keys of an ordered_set in term order, task [#1043](https://github.com/fahchen/pbeam/issues/1043)

Task #1043 adds a sorted list of the keys of an `ordered_set` table, in the ERTS term order. The walk BIFs read it. A key that is not exactly equal to a stored key (`1.0` for `1`) now finds the stored key with a binary search. Before, `key_slot` compared the key with each object of the table, so each insert of a new key walked the whole table.

## Measurement

One session on 2026-10-23 ran release builds of `origin/main` `3a2a6732` and the branch, 11 rounds each, with the order reversed in each other round. Each round ran `pbeam os_bench run -- os_bench.beam` and measured the wall time of the command. The probe module is not a committed fixture. It inserts 20000 integer keys in a scattered order into one `ordered_set` table, then does 20 rounds of `ets:lookup/2` on each key (400000 lookups). The one-minute load was 42.0 at the start and 33.9 at the end, because other sessions ran builds.

| Build | Median (ms) | Min (ms) | Max (ms) |
| --- | --- | --- | --- |
| `origin/main` `3a2a6732` | 1132.0 | 1117.6 | 1171.1 |
| branch | 328.2 | 323.2 | 585.8 |

Commands: `erlc os_bench.erl`, `CARGO_TARGET_DIR=<dir> cargo build --release --bin pbeam` for each revision, and `python3 -I run.py`, which runs the two builds in turn.

## Decision

Land the change. The shape is 3.4 times faster, and the gain comes from the insert of a new key: a binary search replaces the walk of each object. A lookup of an exactly equal key reads the hash index, as before.

## Known gaps

- The host load was high, so the numbers have noise. The gap between the two builds is much larger than the spread.
- The session measured one combined shape. It did not time the inserts and the lookups apart.
- An insert of a new key and a delete move the keys after it in the sorted list, so they cost time in proportion to the table size. The AVL tree of ERTS (`erl_db_tree.c`) costs time in proportion to the logarithm. A `BTreeMap` needs an order with no atom table, and `Term::compare` needs the atom table, so the change keeps a sorted `Vec`.
