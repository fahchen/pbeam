## Measurement record

This record answers the question of task [#633](https://github.com/fahchen/pbeam/issues/633): which mechanism takes the time of the input and output path of a release Terra Counter key press? The section "The attribution of the Terra key press and of the external call at `b8c71940`" of `docs/interpreter-dispatch-measurements.md` (task [#625](https://github.com/fahchen/pbeam/issues/625), PR [#626](https://github.com/fahchen/pbeam/pull/626)) gives that path 5.8 to 6.0 percent of the time of a key and 1.5 percent of its instructions. The measured revision is `8788fe58`, the head of `origin/main` at the time of the session. The task changes no code: the branch adds this record and one backlog entry.

## The method

- **The time probe.** A scratch probe on a copy of `8788fe58` extends the module time probe of task #625. It reads the clock when the run loop starts and stops, when the cursor changes its module (`Cursor::new` and `Cursor::refresh`), and at each read of the terminal, and it gives the wall time between two readings to the module of the cursor. Inside the 21 modules of the input and output group of the #625 record, the probe also reads the clock at each instruction fetch, and it gives each interval to a mechanism key: the instruction kind and its module, from its fetch to the next fetch. A BIF call (`BeamProgram::call_bif`, `src/runtime/interpreter/bif.rs`) and a `bif` instruction get the key of the BIF from the dispatch to the next fetch. A NIF call (`Instruction::NifStart`) gets the key of the NIF, and `prim_tty:read_nif/3` gets one key for each of its steps: the capability check, the `read` system call, the select of fd 0, and the result tuple. A `get_tuple_element` gets a second key from the write of its destination register (`write`, `src/runtime/interpreter.rs:3832`) to the next fetch, with the module and the position of the instruction. The probe work between two clock readings, such as the name of a key, counts for no key and no module.
- **The report.** The probe writes the time of each module and of each key at each read of the terminal, so one report is the time of one key. It keeps the reports in memory and writes them to its file each 20 reports, and the first interval after a write gets its own key (`(after probe write)`). An earlier version of the probe that wrote each report at once gave about 100 µs to 600 µs to the interval after the write, so the write itself disturbed the next interval. The record uses keys 2 to 60 of each run (59 keys). The probe is not committed.
- **The key driver.** The scratch driver of task #625 starts the example `terra_counter` on a pseudo-terminal of 80 by 24 and sends `j` and `k` in turn every 0.5 s, 60 keys for each run. It records the CPU time of the `pbeam` process with `ps -o time` over the keys. Each CPU time here is the raw value of the key window.
- **The floor loops.** The test `records_the_interpreter_dispatch_baseline` (`--exact --nocapture --test-threads=1`) of each revision gives `call_ext_only` and `call_only` in ns for each iteration of 200,000 iterations.
- **The revisions.** The before revision is `8788fe58`. The after revision is the tree of this branch at the time of the session, which had the same code as `8788fe58`: the two release `pbeam` binaries have the same SHA-256 prefix (`e3c8c618336d4fb5`). The interleaved session thus measures the noise of the method.

The largest mechanism is the drop of the old value of a register at a write. One `get_tuple_element` of `gen_server` runs two times for each key, and each run takes about 34 µs, with a maximum of 90 µs to 144 µs for one run. The read of the tuple element before the write takes about 96 ns, so the time is in the write: the write releases the last reference of the old value of the register, and the drop of `Term` (`impl Drop for Term`, `src/term.rs:517`) walks and frees each node of that value that has no other reference ("Drop rule" in `docs/copy-on-write-terms.md`). The record does not identify the dropped value. The size of the drop agrees with the old state of a Terra `GenServer` that holds the last frame, but no probe confirms this. The drop at all positions of `get_tuple_element` is 12.7 to 13.2 percent of the group, and one interval of a `move` in `gen_statem` took 102 µs in run 1 and 324 µs in run 2, so the drops at other kinds of write are part of the other rows too. The input and output path itself is small: the `read` system call is 2.1 to 2.2 percent of the group, and the NIF calls with their steps are 4.4 to 4.8 percent.

ERTS has no such cost at the write. `get_tuple_element` loads one word into the destination (`emit_i_get_tuple_element`, `erts/emulator/beam/jit/arm/instr_common.cpp:378-388`), and the old value of the register becomes garbage with no work. A minor collection copies only the terms that it reaches from the roots (`do_minor`, `erts/emulator/beam/erl_gc.c:1639`, root loop at `:1677`) and then frees the young heap as one block (`erts_deallocate_young_generation`, `erl_gc.c:1831`), so a dead value costs nothing at its last use and nothing at the collection. PBeam keeps the accepted `Arc` graph of terms and has no garbage collector, so the drop of a dead value is paid at the write that releases its last reference.

## The proposal

The proposed change for the largest mechanism is a backlog entry, "Defer the drop of a large dead value out of the instruction path" (`docs/backlog.md`), and not a task. Its upper bound is the drop time of the group, about 110 µs to 117 µs for each key at the `get_tuple_element` writes, which is about 0.8 percent of the 13.6 ms to 14.2 ms of the run loop for each key. A deferred drop moves that time out of the key latency, but it does not remove CPU time, because the same nodes are freed later. The trigger of the entry is a measured workload where the drop of dead values at a register write takes a large part of the time or of the latency.

The other mechanisms above 5 percent of the group are each smaller than the drop row, and each one also runs in the render and library modules, where earlier tasks measure them: `move` (task [#631](https://github.com/fahchen/pbeam/issues/631)), `call_ext` (task [#628](https://github.com/fahchen/pbeam/issues/628)), and `apply` at about 4 µs for each call.

## The decision

No code change lands, so this entry carries the marker **Not landed**. The task is a measurement, and the change that it proposes for the largest mechanism does not reduce CPU time and has an upper bound of about 0.8 percent of the run loop time of a key. The record and the backlog entry land.

## Known gaps

- The probe reads the clock two times for each instruction of the group. Each interval thus holds a fixed part of the probe, about 20 ns to 50 ns, which is the time of the cheapest kinds (`test_yield` 50 ns, `test` 72 ns in run 1). The ns of the short kinds, such as `move` and `test`, are thus upper bounds. The long rows, such as the drop row, change little.
- The clock of the host counts in steps of about 42 ns, so the time of one short interval is not exact. The sums over many intervals are the numbers to use.
- The probe build takes about 7 ms more CPU time for each key than the plain build, and its run loop time for each key (13.6 ms to 14.2 ms) is about equal to the CPU time of the plain build. The probe work outside the intervals can change the state of the caches for the next interval.
- The absolute ms of a key change with the load of the host. Smoke runs of the probe at a one-minute load of 8 to 18, before the session, gave about 7 ms of run loop time for each key and 0.26 ms to 0.30 ms for the group (4.2 percent), against 13.6 ms to 14.2 ms and 0.87 ms to 0.89 ms in the session at a load of 2 to 3. The record uses the shares of the session. The cause of the difference, for example the clock frequency of the cores of a host with little load, is not measured.
- The record does not identify the value that the drop at `gen_server` position 2219 releases, and it does not map that PBeam position to the `beam_disasm` listing of `gen_server`.
- The probe does not count the time before the run loop starts, for example the result of a dirty write or of a pending BIF, which the #625 module probe did not count either.
