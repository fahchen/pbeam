## The method

- **The time probe.** A scratch probe on a copy of `8788fe58` extends the module time probe of task #625. It reads the clock when the run loop starts and stops, when the cursor changes its module (`Cursor::new` and `Cursor::refresh`), and at each read of the terminal, and it gives the wall time between two readings to the module of the cursor. Inside the 21 modules of the input and output group of the #625 record, the probe also reads the clock at each instruction fetch, and it gives each interval to a mechanism key: the instruction kind and its module, from its fetch to the next fetch. A BIF call (`BeamProgram::call_bif`, `src/runtime/interpreter/bif.rs`) and a `bif` instruction get the key of the BIF from the dispatch to the next fetch. A NIF call (`Instruction::NifStart`) gets the key of the NIF, and `prim_tty:read_nif/3` gets one key for each of its steps: the capability check, the `read` system call, the select of fd 0, and the result tuple. A `get_tuple_element` gets a second key from the write of its destination register (`write`, `src/runtime/interpreter.rs:3832`) to the next fetch, with the module and the position of the instruction. The probe work between two clock readings, such as the name of a key, counts for no key and no module.
- **The report.** The probe writes the time of each module and of each key at each read of the terminal, so one report is the time of one key. It keeps the reports in memory and writes them to its file each 20 reports, and the first interval after a write gets its own key (`(after probe write)`). An earlier version of the probe that wrote each report at once gave about 100 µs to 600 µs to the interval after the write, so the write itself disturbed the next interval. The record uses keys 2 to 60 of each run (59 keys). The probe is not committed.
- **The key driver.** The scratch driver of task #625 starts the example `terra_counter` on a pseudo-terminal of 80 by 24 and sends `j` and `k` in turn every 0.5 s, 60 keys for each run. It records the CPU time of the `pbeam` process with `ps -o time` over the keys. Each CPU time here is the raw value of the key window.
- **The floor loops.** The test `records_the_interpreter_dispatch_baseline` (`--exact --nocapture --test-threads=1`) of each revision gives `call_ext_only` and `call_only` in ns for each iteration of 200,000 iterations.
- **The revisions.** The before revision is `8788fe58`. The after revision is the tree of this branch at the time of the session, which had the same code as `8788fe58`: the two release `pbeam` binaries have the same SHA-256 prefix (`e3c8c618336d4fb5`). The interleaved session thus measures the noise of the method.

The time of position 2219 is thus inside the `write` call (`src/runtime/interpreter.rs:3832`), which stores the element in the destination register and releases the old value of that register. The probable cause is the drop of `Term` (`impl Drop for Term`, `src/term.rs:517`), which walks and frees each node of the old value that has no other reference ("Drop rule" in `docs/copy-on-write-terms.md`). The probe does not time the drop apart from the store, and the record does not identify the dropped value. The size of the drop agrees with the old state of a Terra `GenServer` that holds the last frame, but no probe confirms this. The record does not measure the drops at other kinds of write, such as `move`, or at the writes in the modules outside the group. The input and output path itself is small: the `read` system call is 2.1 to 2.2 percent of the group, and the NIF calls with their steps are 4.4 to 4.8 percent.

ERTS has no such cost at the write. `get_tuple_element` loads one word into the destination (`emit_i_get_tuple_element`, `erts/emulator/beam/jit/arm/instr_common.cpp:378-388`), and the old value of the register becomes garbage with no work. A minor collection copies only the terms that it reaches from the roots (`do_minor`, `erts/emulator/beam/erl_gc.c:1639`, root loop at `:1677`) and then frees the young heap as one block (`erts_deallocate_young_generation`, `erl_gc.c:1831`), so a dead heap term costs nothing at its last use and nothing at the collection. A dead off-heap value, such as a large binary, still needs work: the collection sweeps the off-heap list (`sweep_off_heap`, `erl_gc.c:1813`). PBeam keeps the accepted `Arc` graph of terms and has no garbage collector, so the drop of a dead value is paid at the write that releases its last reference.

## The proposal

The proposed change for the largest mechanism is a backlog entry, "Defer the drop of a large dead value out of the instruction path" (`docs/backlog.md`), and not a task. Its measured drop is the `write` call of position 2219 of `gen_server`, about 63 µs to 69 µs for each key in sessions T and U, which is about 0.5 percent of the 12.2 ms to 14.2 ms of the run loop for each key in the same runs. This figure is not an upper bound. A deferred drop also moves the drops at `move` and the other writes, the small drops at the other `get_tuple_element` positions, and the drops in the render and library modules outside the group, and the record does not measure these. A deferred drop moves the drop time out of the key latency, but it does not remove CPU time, because the same nodes are freed later. The trigger of the entry is a measured workload where the drop of dead values at a register write takes a large part of the time or of the latency.

The other mechanisms above 5 percent of the group are `move`, `apply`, and `call_ext`. Each one also runs in the render and library modules, where earlier tasks measure them: `move` (task [#631](https://github.com/fahchen/pbeam/issues/631)), `call_ext` (task [#628](https://github.com/fahchen/pbeam/issues/628)), and `apply` at about 4 µs for each call.

## The decision

No code change lands, so this entry carries the marker **Not landed**. The task is a measurement, and the change that it proposes for the largest mechanism does not reduce CPU time, and its measured drop is about 0.5 percent of the run loop time of a key. The record and the backlog entry land.

## Known gaps

- The probe reads the clock two times for each instruction of the group. Each interval thus holds a fixed part of the probe, about 20 ns to 50 ns, which is the time of the cheapest kinds (`test_yield` 50 ns, `test` 72 ns in run 1). The ns of the short kinds, such as `move` and `test`, are thus upper bounds. The long rows, such as the drop row, change little.
- The clock of the host counts in steps of about 42 ns, so the time of one short interval is not exact. The sums over many intervals are the numbers to use.
- The probe build takes about 7 ms more CPU time for each key than the plain build, and its run loop time for each key (13.6 ms to 14.2 ms) is about equal to the CPU time of the plain build. The probe work outside the intervals can change the state of the caches for the next interval.
- The absolute ms of a key change from run to run and from session to session. The run loop time for each key of the probe builds is 13.63 ms to 14.22 ms in session T and 11.33 ms to 13.54 ms in session U, at a one-minute load of 1.80 to 3.35. The record thus uses the shares of the group. The cause of the difference is not measured.
- The probe does not time the drop apart from the store of the `write` call, and it does not measure the drops at other kinds of write or outside the group.
- The record does not identify the value that the drop at `gen_server` position 2219 releases, and it does not map that PBeam position to the `beam_disasm` listing of `gen_server`.
- The probe does not count the time before the run loop starts, for example the result of a dirty write or of a pending BIF, which the #625 module probe did not count either.
