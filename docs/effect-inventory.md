# Effect inventory

Status: reviewed inventory for transition 1 of the [capability security migration](capability-security-migration.md). This document adds no security mechanism. It does not change runtime behavior. The [security design](capability-security-design.md) defines the terms that this inventory uses.

This inventory lists each effect entry that PBeam executes on the current branch: each BIF, native MFA, instruction path, VM operation, host operation, startup operation, and linked native library. For each entry, it records the authority requirement, the determinism, the execution class, the observable effects, the cost, and the owner. The owner is the Rust module, as a file path, that executes the entry.

A classification in this document is reviewed metadata. It is not a proof about the Rust or C code. The authority labels name the protected domain of each entry. They are not a grant syntax. Transition 2 defines grants.

## Maintenance

Update this inventory in the PR that adds, removes, or changes an entry. The unit test `effect_inventory_lists_each_bif_and_native_function` in `tests/runtime/interpreter/native.rs` reads this file. The test fails in these conditions:

- A BIF that has a body in `BIFS` (`src/runtime/interpreter/bif/table.rs`) has no row in the section "BIFs".
- An `unsupported` entry of `BIFS` is not in the section "Unsupported BIFs".
- A native binding of the static registry has no row in the section "Native bindings".
- A function of a static NIF library that has no binding is not in the section "Native functions without a binding".
- One of these sections lists an entry that the code does not have.

The sections "BIFs" and "Native bindings" also have the column "Capability" (see [Capability](#capability)). The unit test `effect_inventory_names_the_capability_of_each_effect_entry` in the same file fails when a row of these sections has an effect and the cell `none`, has no effect and another cell, or has a cell that is not valid. The integration test `effect_capability` (`tests/integration/effect_capability.rs`) also reads this file. It fails when its probe list does not hold exactly the `kind:operation` pairs of this column, and when a call of a listed entry without its operation does not raise `error:capability_denied`. Thus a new check needs a probe, and a check that the code does not make fails the test.

The tests do not check the other sections. Review them when a PR changes an instruction, a VM operation, a host operation, startup, or a linked library. Tasks #7, #221, and #9 change VM operations. Their PRs update this inventory.

An entry key is `module:name/arity`. The function name is written as it is, also an operator name, for example `erlang:+/2` and `erlang:=/=/2`.

## Classification terms

| `process.send` | A message to another process. |

| `process.link` | A link between two processes. |
| `process.monitor` | A monitor of a process or a port name. |

| `runtime.ets` | ETS tables. |
| `runtime.persistent_term` | Persistent terms. |
| `runtime.atom` | New atoms in the atom table of the run. Atoms are never released. |

| `native.load` | A request to load a NIF library. |

### Capability

The column "Capability" of the sections "BIFs" and "Native bindings" gives the capability check of the entry (transition 2 of the [capability security migration](capability-security-migration.md)). An entry has an effect when its authority has a label other than `none` and `process.self`.

| Value | Meaning |
| --- | --- |
| `none` | The entry has no effect, so it has no check. |
| `kind:operation` | The entry checks the capability `kind` with `operation` after its argument checks and before its first effect. Without it, the entry raises `error:capability_denied` and has no effect. A list gives each check of the entry. |
| `later` | The entry has an effect, and a later batch of [#335](https://github.com/fahchen/pbeam/issues/335) adds its check. Until then, each process can use the entry. |

### Determinism

| Value | Meaning |
| --- | --- |
| `pure` | The result depends only on the arguments. |
| `run` | The result depends on the arguments and the state of the run. The same program, input, and schedule give the same result. |
| `host` | The result or the effect depends on host state outside the run, for example a clock, the environment, or the terminal. |
| `unknown` | This inventory cannot classify the determinism. |

### Execution class

| Value | Meaning |
| --- | --- |
| `inline` | The entry runs to completion on the scheduler thread and makes no host call. |
| `host-call` | The entry runs on the scheduler thread and calls the host or a linked C library. The call does not wait for an external event. |
| `host-blocking` | The entry runs on the scheduler thread, and its host call can wait for an external event, for example a full pipe or a file read. All processes stop until the call returns. |
| `dirty-io` | The calling process switches out, and a dirty IO thread of the run does the host call, which can wait for an external event. The other processes run while the call waits. While the call waits, the scheduler handles the signals of the process. When the call completes, the process goes to the run queue and gets the result in its next turn. When a signal ends the process, a call in the queue does not run, and the scheduler drops the result of a call that runs. |
| `trap` | The entry can continue in BEAM code as a call to an exported function, or in the export of a BIF. The process then switches out, and it continues in the export in its next turn. |
| `scheduler` | The scheduler loop runs the entry. No guest call requests it. |
| `startup` | The entry runs once before the root process starts, or after the run ends. |
| `build` | The entry runs at build time. |

### Cost

`O(1)` is constant. `O(n)` is linear in the size of the argument terms. `O(p)` is linear in the number of live processes. `O(t)` is linear in the number of entries in the shared table that the entry uses. `O(q)` is linear in the length of the signal queue of the process. `O(l)` is linear in the number of links and monitors of the process. `O(d)` is linear in the size of the process dictionary. `O(e)` is linear in the size of the OS environment. `O(s)` is linear in the number of signals that arrived. `O(c)` is linear in the number of dirty IO completions that wait in the inbox. `O(k)` is linear in the size of the capabilities of the caller: their number and the names of their constraints. `O(r)` is linear in the number of delegation records that a revocation reads: the receivers of the copies of the revoker, and the released records below the revoked copy. `O(n log n)` is the average time of a sort of the argument terms. A copy of a term costs `O(n)`. `unknown` means that this inventory cannot give a bound.

### Common BIF behavior

Each BIF runs on the scheduler thread. A call that matches no pattern of the BIF table gives the runtime error `unresolved external MFA`, and the run stops. A BIF result can be a value, an exception, a trap into BEAM code, or the exit of the caller. A runtime error for a part that PBeam does not implement yet stops the run. [ERTS differences](erts-differences.md) records each such part.
