# Performance status

This file is the status document of the performance programme. It holds the rules of the entries and the current state of the headline numbers. Each landed performance change of the interpreter dispatch plan (`docs/interpreter-dispatch-plan.md`) and of the term performance proposal (`docs/term-performance-design-codex-v2.md`) has one entry, with the before value and the after value of the affected shapes. Each entry is a file in `docs/performance/`. The entry file of a new task also holds the measurement record of that task. The measurement records of the earlier tasks are in `docs/interpreter-dispatch-measurements.md`. The task status stays in GitHub Issues.

## The rule of this file

- Each entry is one file in `docs/performance/`. The name of the file is the number of the task issue of the change, for example `docs/performance/627.md`. An entry with no task issue takes the number of its pull request with the prefix `pr-`: `docs/performance/pr-<pull request>.md`.
- The heading of the entry starts with the date of the entry.
- One entry for each landed performance change. A change that only edits documentation takes no entry, because it has no measured effect. An entry for a change that is not landed carries the marker **Not landed** and states the reason.
- Every number names its revision, its session or run group, and its load. A run group is one measurement session with one host load. Two numbers from two sessions are not comparable, because the run-to-run noise is about 10 percent at 200000 iterations.
- A column boundary in a cumulative table is not a measured gain of the later step. Two neighbouring columns come from different run groups, so their difference holds both the change of the code and the noise of the two runs.
- A claim that a change moved a shape needs one session that interleaves the two revisions. One session of one revision alone cannot support that claim.
- Every number comes from a source in this repository or from a merged pull request, and the entry names that source. No entry and no row of this file invents a number or merges two sessions into one comparison.
- A task pull request adds its entry file and does not edit this file. The epic checkpoint, or a separate documentation pull request after the task pull requests merge, updates the `## Current state` table.

The host of every number is Darwin 27.0.0 arm64, an Apple M1 Max with 10 CPUs, unless an entry names another host. The pinned toolchain is `rustc 1.99.0` and `cargo 1.99.0`, and the pinned ERTS is OTP 29, ERTS 17.1, `jit`, `schedulers 10`, `logical processors 10`. The environment table is in `docs/interpreter-dispatch-measurements.md`.

## Entries

The entries are the files in `docs/performance/`, one file for each landed change and one file for each change that is not landed. The heading of each file gives the date, the change, the task issue, and the pull request or the branch.

## How to add an entry

1. Add the file `docs/performance/<task issue>.md` in the pull request that lands the change. Use `docs/performance/pr-<pull request>.md` only for a change with no task issue.
2. Start the file with one heading of level 1 that gives the date, the change, the task issue, and the pull request, for example `# 2026-10-15 15:30 JST - <change>, task [#632](https://github.com/fahchen/pbeam/issues/632), pull request [#638](https://github.com/fahchen/pbeam/pull/638)`.
3. Name the change in one or two sentences, and name the task issue and the pull request.
4. Give the small table of the affected shapes with the before value, the after value, the change, the revision of each column, and the load or the run rule of each column.
5. Put the measurement record of the task in the same file, below the entry, in sections of level 2: for example the change, the session, the results, the decision, and the known gaps. Do not add a section to `docs/interpreter-dispatch-measurements.md`.
6. Name the source of every number: the measurement record in the entry file, a section of `docs/interpreter-dispatch-measurements.md`, the merged pull request, or the plan.
7. Use one session that interleaves the two revisions for a claim that the change moved a shape. Do not compare two sessions, and do not present a column boundary of a cumulative table as a measured gain.
8. State **Not landed** in the heading of an entry whose change is not merged, and state the reason.
9. Do not edit this file in the task pull request. When the new entry changes a headline number, the epic checkpoint or a separate documentation pull request after the merge of the task pull requests updates the `## Current state` table.
